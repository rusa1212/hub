# 테스트 작성 절차 (TDD)

## 0. 대상 함수 선정
- 분기(if/else, 삼항, switch)나 계산 로직(산술/문자열/배열 변환)이 있는 순수 함수를 우선한다.
- fetch/DOM/렌더링만 하는 함수는 후순위.
- 대상 함수가 `export` 되어 있지 않으면, 먼저 `export`를 추가한다 (직접 import해서 테스트하기 위함).

## 1. 테스트 케이스 목록 작성 (코드 작성 전에 반드시 먼저)
다음 4개 카테고리로 나눠서 표로 정리한다.
- **정상 케이스**: 일반적인 입력, 반환 타입/길이/값 검증
- **빈 값 케이스**: 빈 배열/빈 문자열/0 등
- **경계값 케이스**: 최소 크기(1개), 대용량, 극단값(최대/최소), 홀짝 등
- **실패/비정상 케이스**: null/undefined, 타입이 다른 입력, 길이 불일치 등 — 여기서 기존 구현의 잠재 버그가 자주 발견됨. 발견되면 "현재 동작을 그대로 문서화할지" vs "고칠지"를 먼저 결정한다.

## 2. RED — 실패하는 테스트 먼저 작성
- 파일명: `<대상파일명>.test.js`, 대상 소스와 같은 디렉터리에 위치 (예: `src/foo.js` → `src/foo.test.js`)
- import: `import { describe, it, expect } from 'vitest'` + 대상 함수를 상대 경로로 import
- `describe`를 카테고리별로 나누고, `it` 이름에 케이스 ID(N1, E1, B1, F1 등)를 붙여 계획 목록과 1:1 매핑되게 한다.
- 실행: `npm test` (front 디렉터리 기준) 또는 `npx vitest run <파일경로>`
- 새로 추가한 테스트가 **의도한 이유로 실패하는지** 확인한다 (엉뚱한 이유로 실패하면 테스트 자체를 재검토).

## 3. GREEN — 테스트를 통과시키는 최소 구현
- 테스트를 통과시키는 데 필요한 최소한의 코드만 수정한다. 과도한 리팩터링은 이 단계에서 하지 않는다.
- 재실행해서 새 테스트가 모두 통과하는지 확인한다.

- 테스트를 통과시키는 데 필요한 최소한의 코드만 수정한다. 과도한 리팩터링은 이 단계에서 하지 않는다.
- 재실행해서 새 테스트가 모두 통과하는지 확인한다.

## 4. REFACTOR — 충돌하는 기존 테스트 정리
- 동작 변경으로 인해 예전 동작을 "문서화"하던 기존 테스트가 깨질 수 있다. 삭제하거나 새 동작에 맞게 수정한다.
- 전체 스위트(`npm test`)를 재실행해서 회귀가 없는지 확인한다.

## 5. 완료 조건
- 계획 단계에서 나열한 모든 케이스(정상/빈값/경계값/실패)가 테스트로 존재하고 전부 GREEN.
- `npm test` 전체 스위트 통과.
